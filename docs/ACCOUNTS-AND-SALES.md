# Личный кабинет и подготовка продаж

Решение владельца: **разовая покупка для одного пользователя, вход по e-mail, бессрочный доступ без автопродления**. Привязки покупки к конкретному велосипеду нет. 299–499 ₽ — ориентир, окончательная цена и платные возможности ещё не утверждены.

## Что работает

- Кнопка «Кабинет» на главной и в конфигураторе: обзор, карточка велосипеда, реальные локальные профили и копии, история покупок.
- Без сервера карточка сохраняется с проверкой чтения в `prefs/account.card.v1` существующей IndexedDB. При недоступном хранилище сохранение и экспорт отключены. Начальные поля пустые: Trek/48 В/19,2 А·ч — подсказки, а не данные нового посетителя.
- Локальная карточка не является аккаунтом. Подпись «На этом устройстве» объясняет границы хранения. Профиль мотора, черновик редактора, настройки расчёта и справочная карточка велосипеда независимы.
- Отдельный Node.js-сервис: вход по шестизначному коду из письма, серверная карточка велосипеда, сохранение с номером редакции, выход, чтение истории покупок и права доступа. Код не приходит в HTTP-ответе и не печатается в журнале.
- После входа карточка берётся из аккаунта; локальная карточка не загружается на сервер автоматически. Кнопка «Взять карточку с этого устройства» только заполняет форму. Сохранение требует отдельного действия.
- Настройки мотора и резервные копии не отправляются в облако. Их список всегда помечен как файлы текущего браузера; архив содержит карточку и эти файлы, без кодов и сессий.
- Демо доступа не создаёт оплаченный заказ. `/api/checkout` выключен. Покупки не выдумываются, клиент не может передать `paid=true`, чтобы получить серверное право.

## Граница готовности

Кабинет и сервер входа реализованы и тестируются, но **не являются запущенным платным сервисом**. На GitHub Pages работает только локальный кабинет; Node.js там не исполняется. Для e-mail требуются работающий отдельный сервер, SMTP и опубликованная политика обработки данных. Сбор персональных данных не включается без ссылки на эту политику.

Оплата, чеки, возвраты, удаление аккаунта, восстановление БД из резервной копии и коммерческий доступ к возможностям ещё не реализованы. Не брать деньги до их готовности. Публичный браузерный исходный код нельзя считать надёжной платёжной защитой: права платного сервиса должны проверяться сервером на каждой соответствующей операции. Что именно входит в покупку, нужно определить до подключения кассы. Не блокировать подпиской восстановление исходных настроек, экспорт копий или уже начатую операцию с мотором.

## Запуск сервера входа

Node.js 24.19+. Код в `server/` имеет собственный lockfile и одну зависимость — Nodemailer. Статический клиент новых внешних зависимостей не получил.

1. В отдельном каталоге приложения выполнить `npm ci --omit=dev --ignore-scripts` внутри `server/`.
2. Скопировать `server/.env.example` в `server/.env`; заполнить секрет, адрес HTTPS-сайта, абсолютный путь БД вне публичного дерева, SMTP и ссылку на опубликованную политику. Собственный проверенный документ можно разместить как `privacy.html` в корне приложения; он разрешён статическим сервером. Шаблон с выдуманными реквизитами не поставляется. Реальные значения не хранить в Git. Запускать от отдельного непривилегированного пользователя.
3. Запустить `npm start` внутри `server/`. Процесс слушает только `127.0.0.1:8787`. Собственный HTTPS reverse proxy должен направлять корень сайта и `/api/` на него, сохраняя Host. Не применять старые скрипты проекта, меняющие чужой nginx.
4. Сервер отдаёт только разрешённые публичные файлы. `.env`, SQLite, исходники сервера и зависимости через HTTP не выдаются. В двух HTML он включает same-origin API через метатег; на статическом хостинге этот метатег пустой и запросов к несуществующему API нет.
5. Установить лимит тела запроса 8 КБ и дополнительные лимиты частоты на reverse proxy. API намеренно не доверяет `X-Forwarded-For`: его ограничение по IP за прокси общее, поэтому перед ростом нагрузки настройку реального IP нужно отдельно спроектировать и протестировать.
6. Проверить доставку писем в тестовые ящики владельца, повторный вход после перезапуска, logout, истечение сессии, сохранение/конфликт карточки и отсутствие утечек данных через HTTP. Не включать SMTP debug-журнал.

БД SQLite использует WAL, внешние ключи и транзакцию при создании сессии. Одноразовый код живёт 10 минут, допускает 5 попыток; повторная отправка аннулирует старый код. Лимиты по адресу и IP сохраняются в БД. Сессия имеет абсолютный срок 7 дней; в БД хранится HMAC токена. Cookie — HttpOnly, SameSite=Strict и Secure/__Host- на HTTPS. Изменяющие запросы требуют совпадающего Origin и JSON. На локальном HTTP допускается только localhost/127.0.0.1. Все ответы API — no-store.

## Контракт API

| Метод | Путь | Результат |
|---|---|---|
| GET | `/api/account` | `user`, `access`, `orders`, доступность входа/оплаты, версия политики, продукт |
| POST | `/api/auth/request` | `{email, privacyVersion}` → идентификатор проверки; код отправляется только почтой |
| POST | `/api/auth/verify` | `{challenge, code}` → профиль; сессия только в HttpOnly cookie |
| POST | `/api/auth/logout` | отзывает текущую сессию |
| POST | `/api/profile` | `{profile, revision}` → сохранённая карточка и новая редакция; при конфликте 409 |
| POST | `/api/checkout` | 503, оплата пока выключена |

Вход создаёт один аккаунт на нормализованный e-mail. Раздельная регистрация не нужна. Нет формы пароля, смены e-mail, recovery-токенов или скрытого административного доступа. Авторизация не зависит от IndexedDB. Демо-состояние в интерфейсе никогда не используется сервером для выдачи прав.

## Следующий этап: приём оплаты

Подготовлены таблицы `orders` и `entitlements`. При подключении провайдера (кандидат — ЮKassa) соблюдать следующий контракт:

1. Сервер выбирает утверждённый продукт и цену в копейках, создаёт заказ для текущей сессии. Цена, пользователь и статус не берутся из клиентского тела запроса. Защита от повторного клика и повторной покупки уже действующего доступа обязательна.
2. Стабильный idempotence key привязан к заказу. После неопределённого ответа не создавать следующий платёж с новым ключом; сверять исходный запрос. Учесть срок идемпотентности провайдера.
3. Подтверждать оплату серверным запросом к API провайдера: сверять ID, сумму, RUB, магазин, metadata заказа, тестовый/боевой режим и успешный статус. Redirect, сообщение браузера или непроверенный webhook не являются оплатой.
4. В одной транзакции помечать заказ оплаченным и выдавать бессрочное право пользователю. Повторный webhook не выдаёт вторую покупку; чужой order ID не раскрывается другому пользователю.
5. Обработать отмены и возвраты, переупорядоченные уведомления, потерянный webhook, ручную сверку, восстановление после сбоя. Чеки и сведения продавца подключаются в соответствии с фактической схемой работы продавца — не подставлять выдуманные реквизиты или документы.
6. Только после sandbox-тестов полной цепочки, утверждения цены/условий/возвратов и проверки боевого сервера включать `checkoutEnabled`. Сейчас эта возможность намеренно отсутствует.

Источники для интеграции: [Nodemailer SMTP](https://nodemailer.com/smtp), [OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html), [OWASP Sessions](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html), [ЮKassa: уведомления](https://yookassa.ru/developers/using-api/webhooks), [ЮKassa: идемпотентность](https://yookassa.ru/developers/using-api/interaction-format).
